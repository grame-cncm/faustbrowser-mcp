# Faust Library Documentation Tools Integration Plan

## Goal

Add Faust library documentation search and retrieval features to
`faustbrowser-mcp` by reusing the behavior currently implemented in
`faust_doc_api.py` in the `faustlibraries` project.

The target tool surface is:

- `search_faust_lib(query, limit?, module?)`
- `get_faust_symbol(symbol)`
- `list_faust_module(module, limit?)`
- `get_faust_examples(symbol_or_module, limit?)`
- `explain_faust_symbol_for_goal(symbol, goal)`

These tools should run locally inside the Python MCP server and should not
depend on an active browser runtime session.

## Scope

This integration should:

- support the Faust documentation JSON generated by `faustlibraries`
- support only the split JSON layout generated by `make doc-index-split`
- expose the five documentation tools as MCP tools
- keep the implementation local to `faustbrowser-mcp`
- document setup and usage in the project README

This integration should not:

- route documentation queries through the browser bridge
- require audio to be running
- require Faust compilation just to answer library documentation questions

## Recommended Architecture

### 1. Keep the documentation logic local to `faustbrowser-mcp`

Do not call `faust_doc_api.py` through `subprocess`.

Instead, port the reusable core logic into a local Python module in this
repository, for example:

- `faust_doc_tools.py`

This avoids:

- hard-coded dependencies on another repository path
- process-spawning overhead
- awkward error handling through CLI stdout/stderr
- reduced testability

### 2. Reuse the same data model and lookup behavior

Port the core pieces from `faust_doc_api.py`:

- JSON loading
- split index handling
- module resolution
- symbol ranking
- exact symbol lookup
- fuzzy symbol fallback
- example extraction
- action-oriented explanation generation

The goal is behavior compatibility with `faustlibraries` and `faustforge`,
without copying the CLI layer.

### 3. Keep documentation tools separate from browser runtime tools

`faustbrowser-mcp` already has two clear runtime concerns:

- browser bridge and DSP runtime control
- MCP tool exposure

The Faust library documentation tools should form a third local-only concern:

- local JSON-backed library documentation retrieval

They should not depend on:

- browser registration
- AudioContext state
- compile/start lifecycle

## Implementation Plan

### Phase 1. Introduce a local documentation backend module

Create a Python module in `faustbrowser-mcp`, for example:

- `faust_doc_tools.py`

Responsibilities:

- load a top-level documentation index
- validate that it is a split index
- lazily load module payloads
- expose Python functions equivalent to:
  - `search_faust_lib`
  - `get_faust_symbol`
  - `list_faust_module`
  - `get_faust_examples`
  - `explain_faust_symbol_for_goal`

Recommended contents:

- `FaustDocStore`
- `load_json`
- `normalize_module_key`
- `rank_symbol_match`
- `module_doc_relpath_for_source`
- one function per MCP-facing operation

Do not copy:

- `argparse`
- CLI-only formatting concerns

### Phase 2. Define configuration for the documentation index

Add explicit configuration for the index location.

Recommended environment variable:

- `FAUST_DOC_INDEX`

Expected accepted values:

- path to a split index file
- path to a split index directory containing `index.json`

Recommended fallback strategy:

1. `FAUST_DOC_INDEX` if defined
2. a repository-local default if one is later shipped with the project
3. otherwise fail with a clear runtime message

Error behavior should be explicit:

- if the index is missing, tools should return a clear message explaining that
  `faustbrowser-mcp` expects a split index generated by `faustlibraries`
- this should not look like a browser bridge failure
- if a monolithic JSON is provided, tools should fail fast with a clear error

### Phase 3. Add MCP tools to the Python server

In `faust_browser_server.py`, add five new MCP tools:

- `search_faust_lib(query: str, limit: int = 10, module: str | None = None)`
- `get_faust_symbol(symbol: str)`
- `list_faust_module(module: str, limit: int = 200)`
- `get_faust_examples(symbol_or_module: str, limit: int = 10)`
- `explain_faust_symbol_for_goal(symbol: str, goal: str)`

Behavior should match the current local API:

- `search_faust_lib`
  - search compact symbol summaries
  - optional module filtering

- `get_faust_symbol`
  - return the full symbol entry
  - include alternatives

- `list_faust_module`
  - resolve module by name, path stem, or alias
  - return lightweight symbol summaries

- `get_faust_examples`
  - prefer exact module resolution first
  - then fall back to symbol lookup
  - avoid ambiguous behavior for names like `motion`

- `explain_faust_symbol_for_goal`
  - use `summary`, `usage`, `params`, `notes`, and `testCode`
  - keep the result short and action-oriented

### Phase 4. Add a shared loader/helper inside the server

To avoid repeated file IO and repeated store construction:

- initialize the documentation store lazily
- cache it in-process
- reuse it across tool calls

Recommended helper shape:

- `_get_faust_doc_store()`

This helper should:

- read configuration
- instantiate the store once
- raise a clear exception if configuration is invalid or if the provided index
  is not a split-layout index

### Phase 5. Document the feature in the README

Update `README.md` in `faustbrowser-mcp` with:

- what the new documentation tools do
- how to generate the documentation index in `faustlibraries`
- how to point `faustbrowser-mcp` to that index
- the accepted `FAUST_DOC_INDEX` formats
- examples of each new MCP tool

Recommended documentation topics:

- prerequisites
- configuration
- tool list
- example calls
- failure mode when no index is configured

## Data Compatibility Requirements

The implementation should work with the split JSON generated by
`build_faust_doc_index.py` in `faustlibraries`.

Important fields expected in full symbol entries:

- `id`
- `name`
- `qualifiedName`
- `summary`
- `usage`
- `params`
- `notes`
- `io`
- `testCode`
- `references`
- `source`

Important fields expected in compact split index entries:

- `id`
- `name`
- `qualifiedName`
- `summary`
- `usage`
- `io`
- `source`
- `hasTestCode`
- `notesCount`
- `referencesCount`

Important fields expected in library entries:

- `file`
- `path`
- `aliasHints`
- `moduleDoc`

## Behavioral Requirements

### Module lookup

Module resolution should accept:

- module filename stem, such as `filters`
- source path stem, such as `dx7/env`
- alias hint, such as `fi` or `pm`

### Symbol lookup

Exact lookup should check:

- `name`
- `id`
- `qualifiedName`

If exact lookup fails, the ranking heuristic should match the current behavior:

- exact `qualifiedName` strongest
- exact `name` next
- exact `id` next
- otherwise accumulate score from:
  - `name`
  - `qualifiedName`
  - `summary`
  - source filename

### Example lookup

`get_faust_examples` should:

1. try exact module lookup first
2. if no module matches, try symbol lookup

This avoids incorrect results for ambiguous short queries.

### Explanation generation

`explain_faust_symbol_for_goal` should not attempt advanced DSP inference.

It should synthesize a recommendation string from:

- symbol identity
- summary
- usage
- parameter descriptions
- notes
- test snippet availability

## Validation Plan

After implementation, validate with a real split index generated by
`faustlibraries`.

Minimum smoke tests:

### Index loading

- load a split index file
- load a split index directory
- reject a monolithic JSON with a clear error

### Tool behavior

- `search_faust_lib("delay")`
- `get_faust_symbol("filters.highpassLR4")`
- `get_faust_symbol("pm.SFFormantModel")`
- `list_faust_module("physmodels")`
- `get_faust_examples("motion")`
- `get_faust_examples("pm.SFFormantModel")`
- `explain_faust_symbol_for_goal("motion.orientation6", "...")`

### Edge cases

- missing or unreadable index path
- ambiguous module/symbol names
- split index with nested module paths such as `modules/dx7/env.json`
- symbols with `notes`
- symbols with no `testCode`

## Recommended Order of Work

1. Add `faust_doc_tools.py`
2. Port and validate the store and lookup functions
3. Add the five MCP tools in `faust_browser_server.py`
4. Test with a real index from `faustlibraries`
5. Document setup and examples in `README.md`

## Success Criteria

The work is complete when:

- all five documentation tools are available from `faustbrowser-mcp`
- they work without a browser runtime connection
- they support the split JSON format generated by `faustlibraries`
- they return results consistent with the split-index behavior of `faust_doc_api.py`
- ambiguous queries like `get_faust_examples("motion")` behave correctly
- setup and usage are documented in the project README
